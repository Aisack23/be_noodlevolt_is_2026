# feat(BE-06): registrar pagos simulados y comprobantes no fiscales

## Qué cambia

- Se implementa `POST /api/v1/payments/simulate` para el cliente propietario del pedido.
- `test_4242` aprueba y `test_0002` rechaza tras una demora simulada de dos segundos.
- Se registra cada resultado con HTTP 201 y `status: APROBADO` o `RECHAZADO`.
- Los importes se calculan con precios históricos de OrderItem y aritmética decimal; no se acepta el importe del navegador.
- Se permite conservar rechazos y reintentar. Un pedido ya aprobado responde 409 ante un nuevo intento.
- La aprobación y su comprobante no fiscal se guardan en la misma transacción.
- Se añade bloqueo de pedido, índice único parcial para un aprobado por pedido y unicidad de comprobante por pago.
- Solo se persisten últimos cuatro dígitos, resultado y motivo; no se aceptan ni almacenan PAN, CVV ni tokens de prueba.
- Se añaden documentación y pruebas de HTTP, seguridad, demora y restricciones PostgreSQL.

## Alcance y compatibilidad

- La rama parte de develop y no incluye cambios de BE-01 ni BE-02 pendientes.
- Se reutilizan los estados internos PAID y REJECTED; la API los presenta como APROBADO y RECHAZADO.
- La relación Order.payment pasa a Order.payments para conservar varios intentos.
- PaymentRepository.findByOrder devuelve el intento más reciente. Consultas que necesiten aprobación deben filtrar PAID.
- Se añade una migración y SimpleReceipt, separado de los documentos fiscales existentes.

## Qué queda fuera y por qué

- Puntos: corresponde a HU-07; no se acredita saldo en esta entrega.
- Reportes: corresponde a HU-10; deberán sumar exclusivamente PAID.
- Pasarela bancaria real: el alcance es una simulación con tokens de prueba.
- CI: las comprobaciones se ejecutaron en el entorno de desarrollo; no se añadió un workflow.
