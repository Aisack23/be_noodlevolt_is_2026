# fix(BE-06): limitar pagos a pedidos para llevar y cerrar validación de HU-06

## Qué cambia

- Se exige Order.type=TAKEOUT en la prevalidación y dentro de la transacción que registra el pago.
- DINE_IN y DELIVERY propios responden 409 sin crear pagos ni comprobantes.
- Se conserva la comprobación de titularidad antes de revelar conflictos de negocio, y el bloqueo FOR UPDATE más el índice único parcial para impedir doble aprobación.
- Se documenta el nuevo conflicto en Swagger.
- Se corrige unknown en Supertest.send y la importación incompatible de supertest/types, sin casts a any ni supresiones.
- Se protege el cierre de la aplicación del test base si falló su inicialización.
- Se retira una importación sin uso de BranchRepository para dejar lint sin advertencias.
- Se añaden cuatro pruebas de repositorio y tres E2E, y se refuerzan las aserciones de rechazo y segundo cobro.
- Se actualiza la documentación con la regla de estados y los resultados finales de validación.

## Criterios de aceptación de Trello

- [x] Pedido pendiente y test_4242: responde 201/APROBADO; se registra Payment PAID y comprobante simple en la misma transacción.
- [x] test_0002: responde 201/RECHAZADO; se conserva Payment REJECTED con totalPaid=0, sin comprobante y el pedido sigue sin pagar.
- [x] Pedido ya aprobado: nuevo cobro responde 409 sin añadir otro intento ni otro aprobado/comprobante.
- [x] Dos pagos concurrentes producen un solo aprobado, protegido también por PostgreSQL.
- [x] Solo CLIENT puede pagar y únicamente pedidos propios TAKEOUT no cancelados.

## Contrato

```http
POST /api/v1/payments/simulate
Authorization: Bearer <accessToken>
Content-Type: application/json
```

```json
{
  "orderId": "20000000-0000-4000-8000-000000000001",
  "cardToken": "test_4242"
}
```

Tokens: test_4242 aprueba y test_0002 rechaza, con demora simulada de dos segundos.
Los dos resultados registran un intento y responden HTTP 201: frontend debe
consultar status y no asumir que todo 201 representa aprobación.

El importe se calcula con precios históricos de las líneas. No se reciben
importe, PAN, CVV ni propietario. Solo se guardan last4, resultado y motivo.
PAID/REJECTED siguen siendo estados internos; la API devuelve APROBADO/RECHAZADO.

## Regla de estado

Pendiente de pago significa ausencia de un Payment PAID. Se admite pagar un
pedido propio TAKEOUT no cancelado aunque cocina haya avanzado de PENDING:
el documento permite preparar antes de pagar. No se cambia el estado de
preparación al cobrar. Se rechazan CANCELED y los tipos DINE_IN/DELIVERY.

## Cómo probarlo

Con Prisma Client generado y una base PostgreSQL exclusiva de pruebas migrada:

```bash
npm ci
npm run prisma:generate
npm run prisma:deploy
npx tsc --noEmit
npm run build
npm run lint
npm test
npm run test:e2e
```

Para ejecutar solo pagos:

```bash
npx vitest run src/payments/simulation/services/simulated-payments.spec.ts src/payments/simulation/repositories/simulated-payments.repository.spec.ts
npx vitest run --config vitest.config.e2e.ts test/db-simulated-payments.e2e-spec.ts test/db-simulated-payments-schema.e2e-spec.ts
```

En el entorno cloud se generó el cliente con APIs oficiales Prisma 7.10.0 y WASM
local, sin desactivar TLS ni checksums. La ejecución E2E utilizó una base temporal
con todas las migraciones de esta rama, que se eliminó al terminar. No se
alteraron datos de desarrollo. La CLI nativa puede requerir permitir
binaries.prisma.sh en entornos con la misma política restringida.
